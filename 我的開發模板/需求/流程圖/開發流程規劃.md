## Context（為何產出這份規劃）

使用者即將開始實作 POS 系統，UI 已委由另一 AI 產出 Figma 檔案，現在需要一份「可直接落地」的開發流程規劃。專案的特殊架構有兩層：

1. **POS 專案本身**（根目錄 = [`/Users/wei/Desktop/code/POS/`](/Users/wei/Desktop/code/POS/)）— 實際要出貨的產品程式碼
2. **[模塊化組件/](模塊化組件/) 共用元件庫** — 跨專案複用的模組倉儲。目前已有四個模組接近完成（`module-common` ✅、`module-auth` ✅ 含 POS 擴展、`module-organization` ✅ 含 POS 擴展、`module-workflow` 🟡 骨架），且存在一些待修復項目（`module-notification` compile 失敗、`module-attendance` 無測試）

工作流程是**「邊開發模塊邊寫專案」**：在 POS 專案下工作，但通用的模組改動要同步回 `模塊化組件/` 以供未來其他專案複用。

因此這份規劃要做的是：
1. 盤點 `模塊化組件/` 既有模組的完成度與可複用資產，避免重複造輪子
2. 明訂「從 `模塊化組件/` bootstrap 到 POS 專案 → 開發 → 同步回 `模塊化組件/`」的工作流程
3. 界定「先修復」的遺留問題（compile 失敗、骨架服務），才能安全往上疊 POS 模組
4. 依照 [需求文檔.md](我的開發模板/需求/需求文檔.md) 的 23 模組優先級，拆成可交付的 Sprint 節奏
5. 明訂模組化規範、前端共用庫補強項、測試與驗證流程，讓後續開發 AI 或人類協作者都能一致落地

**同步工作流程**（cross-cutting requirement）：
- POS 專案下的開發是主要工作
- 當 `POS/backend/module-common/` 或其他共用模組發生**可複用的改動**（bug 修復、通用工具新增、共用 Hook/組件），必須同步複製回 [`模塊化組件/module/backend/module-*/`](模塊化組件/module/) 對應位置
- 當在 POS 下新建了**可被其他專案複用的模組**（如 `module-system`、`module-audit`、`module-report`），同步複製進 `模塊化組件/module/backend/`
- **POS 專屬模組**（`module-pos-*` 系列）**也要同步**到 `模塊化組件/`，因為這些模組本身就是 POS 這個業態的模板化組件
- 同步動作每個 Sprint 結束時做一次（作為 DoD 的一部分，詳見第八節）
- 純粹 POS 業務邏輯（如具體的店家 seeder 資料、特定整合設定）不需同步

新模組一律命名為 `module-pos-*`，資料表前綴 `pos_*`（依 [需求文檔.md §6.1](我的開發模板/需求/需求文檔.md)）。

### 2.2 模組分類與處理方式

| 類型 | 處理方式 | 模組 |
|------|---------|------|
| **直接複用** | 不動程式碼，只在 `application.yml` 打開 `modules.*` 開關 | module-common、module-audit（新建 common 層 AOP 即可）、module-system（新建設定 CRUD 即可） |
| **修復後複用** | 先清遺留問題 | **module-notification**（修 compile）、**module-workflow**（補 WorkflowEngine 引擎邏輯） |
| **複用＋POS 擴展（已做）** | 無需再動主結構，僅在後續 Sprint 視需求補欄位 | module-auth、module-organization |
| **全新開發** | 依 [需求文檔.md](我的開發模板/需求/需求文檔.md) §4 各模組規格建立 | pos-core / pos-product / pos-payment / pos-inventory / pos-tax / pos-crm / pos-staff / pos-promotion / pos-printing / pos-sync / pos-hardware / pos-kitchen / pos-table / pos-delivery / pos-supplier / pos-reservation |
| **改用新模組取代** | POS 排班 ≠ ERP 打卡，設 `modules.attendance: false`，由 `module-pos-staff` 取代 | module-attendance |

### 2.3 跨模組通訊原則（沿用 module-rules 規範）
- **強依賴**：直接 `@Autowired` Service Interface（同 JVM）
- **弱依賴**：Spring `ApplicationEventPublisher` + `@EventListener`
- **選配依賴**：`@Autowired(required = false)`，使用前 null-check（對應 Feature Toggle 關閉場景）
- **禁止**：跨模組直接存取對方 Repository、直接 new 另一模組的 Entity 做 JPA 操作

### 8.2 Git 分支策略與 Code Review 準則

**分支模型**：
```
main    ──────── 正式發布（每 Phase 結束，打 tag v0.x.0-phaseN）
 └ develop ──── 開發主線（每 Sprint 結束 merge）
    ├ feature/phase0-fix-notification
    ├ feature/phase0-workflow-engine
    ├ feature/pos-product
    ├ feature/pos-core
    ├ fix/xxx
    └ sync/module-common-update   # 專門做 POS → 模塊化組件 同步的分支
```

**分支規則**：
- 每個 Sprint 一個 feature 分支 → PR 至 `develop`
- 跨模組依賴：**先 merge 被依賴者**（如 `pos-product` 必須先於 `pos-core`）
- 每 Phase 結束 `develop` → `main`，打 tag `v0.1.0-phase1`、`v0.2.0-phase2`
- 模塊化組件同步獨立分支 `sync/xxx`，專門處理「POS 改動回寫共用元件庫」，避免與業務 PR 混雜

**跨模組 PR 依賴處理**：
- PR 描述必須標註：`依賴 PR: #123 (需先 merge)`
- 使用 Draft PR 當被依賴者尚未 merge 時先開草稿
- CI 允許 base branch 選擇被依賴 PR 的 branch（而非直接 develop），以利測試

**Code Review 檢查清單**（Reviewer 必看，對應 module-rules 的高內聚低耦合原則）：

| 檢查項目 | 具體檢查方式 |
|---------|------------|
| **禁止跨模組呼叫 Repository** | `grep -r "XxxRepository" module-yyy/` 應為空；A 模組要讀 B 資料必須透過 B 的 Service Interface |
| **禁止跨模組 new 對方 Entity 做 JPA 寫入** | Code Review 看有無 `new SomeOtherModuleEntity()` 並呼叫 `repository.save()` |
| **Entity 繼承 BaseEntity** | 所有 JPA Entity 必須 `extends BaseEntity`，含 `createdAt/updatedAt/deletedAt` |
| **金額欄位用 BigDecimal** | 禁用 `double`/`float`/`Double`/`Float`；前端顯示透過 `moneyFormat` util |
| **@ConditionalOnModule 正確設置** | 每個模組的 `XxxModuleConfig` 要有 `@ConditionalOnModule("xxx")`，確認 `matchIfMissing` 值 |
| **選配依賴有 null-check** | `@Autowired(required = false)` 的 Bean 使用前必先 `if (service != null)` |
| **事件命名一致** | 事件類放在 `com.enterprise.xxx.event` 套件，命名 `XxxEvent`；發布者與消費者皆有對應 [需求文檔](我的開發模板/需求/需求文檔.md) 章節記載 |
| **跨模組關聯只記 ID** | 不建 DB Foreign Key 到其他模組的表；關聯欄位用 `storeId/orderId/itemId` 等 UUID |
| **Flyway 版號依規範** | `V[模組前綴][三位序號]__describe.sql`；新表前綴對齊 `pos_xxx_*` |
| **Controller 統一回應格式** | `ResponseEntity<ApiResponse<T>>`；錯誤拋 `BusinessException` 由 `GlobalExceptionHandler` 處理 |
| **單元測試覆蓋率** | Service 層 ≥ 80%，核心引擎類（PricingEngine/WorkflowEngine/ZReportCalculator）≥ 90% |
| **OpenAPI 註解** | Controller 有 `@Operation`、`@Parameter`、`@ApiResponse` |
| **敏感操作加 @Auditable** | 退款、作廢、折扣、現金抽屜、PIN 錯誤、權限變更都必須掛 `@Auditable` |
| **同步回模塊化組件** | 若改動的是共用模組（module-common、module-auth、module-organization、module-workflow、module-notification）或前端 `shared/`，PR 描述必須列出已同步的檔案清單 |

**Merge 條件**（缺一不可）：
- [ ] CI 全綠（單元測試 + 整合測試 + lint + build）
- [ ] 覆蓋率 gate 通過（新增/修改 Service 方法覆蓋率 ≥ 80%）
- [ ] 至少 1 位 Reviewer approve
- [ ] 跨模組改動者需 2 位 approve（其中一位必須是被影響模組的 owner）
- [ ] 同步回模塊化組件的檔案已列在 PR 描述

### 8.3 測試策略（對齊 [開發與測試整合規劃書](模塊化組件/開發與測試整合規劃書.md)）

**8.3.1 後端單元測試（JUnit 5 + Mockito + AssertJ）**

| `module-workflow` | **`WorkflowEngine`** | 啟動流程、審批通過/駁回/轉簽、會簽或簽判定、條件分支 |
| `module-pos-core` | **`PricingEngine`** / `OrderStateMachine` / `OrderService` | 稅額／折扣／找零計算、狀態轉換合法性、併發下單 |

### 8.4 Feature Toggle 三層機制與灰度發布

**三層切換機制**（由淺入深）：

| 層級 | 機制 | 粒度 | 用途 |
|------|------|------|------|
| **編譯層** | `@ConditionalOnModule("xxx")`（自訂 annotation，底層 `@ConditionalOnProperty`） | Bean 是否註冊 | 模組完全停用時 JVM 不載入，零性能損耗 |
| **配置層** | `application.yml` 的 `modules.xxx: true/false` | Spring Profile 粒度 | 業態預設（retail/fastfood/...）切換 |
| **運行層** | DB 表 `sys_feature_toggles`（Phase 2 Sprint 2-4 與 module-system 一起建） | 租戶/門店/使用者粒度 | 灰度發布與 A/B 測試 |

**開關命名規範**：
- 模組層：`modules.[模組名]`（如 `modules.pos-crm`）
- 功能層：`pos.[模組].[功能]`（如 `pos.promotion.coupon-enabled`）
- 所有開關在 [需求文檔 §10.2](我的開發模板/需求/需求文檔.md) 業態配置表統一管理

**新增模組的 Feature Toggle 檢查清單**：
- [ ] 該模組的 `XxxModuleConfig` 加 `@ConditionalOnModule("xxx")`
- [ ] `application.yml` 加 `modules.xxx: [預設值]`
- [ ] 5 份業態檔（retail/fastfood/restaurant/cafe/chain-hq）都加對應開關（避免後續忘記）
- [ ] 關閉時的回退邏輯已處理（前端隱藏選單、後端選配依賴 null-check）
- [ ] 測試：關閉開關後 `mvn spring-boot:run` 仍能啟動、不報錯

**灰度發布流程**（新模組上線時）：

```
┌─────────────────────────────────────────────────────────────────┐
│  Step 1: 開發 feature 分支，merge 到 develop 時 modules.xxx=false │
│    ↓                                                             │
│  Step 2: CI 自動跑 "profile-all-off" 測試 (驗證老模組不受影響)    │
│    ↓                                                             │
│  Step 3: 內部測試環境打開，跑回歸套件 + 新模組單元+整合測試        │
│    ↓                                                             │
│  Step 4: Staging 單一業態打開（如先只在 retail profile）          │
│    ↓                                                             │
│  Step 5: Staging 全業態打開，跑 5 套 E2E 快樂路徑                 │
│    ↓                                                             │
│  Step 6: 生產環境按租戶/門店分批 rollout（用 sys_feature_toggles） │
│     - 第一批：1 家門店，觀察 24 小時                              │
│     - 第二批：10% 門店，觀察 3 天                                 │
│     - 第三批：50%，觀察 1 週                                      │
│     - 全量上線                                                    │
│    ↓                                                             │
│  Step 7: 移除灰度開關（或改為永久性功能開關）                      │
└─────────────────────────────────────────────────────────────────┘
```

**「新模組不影響舊模組」CI Gate**（Phase 2 起引入）：
- CI 額外跑一輪 `mvn verify -Dspring.profiles.active=test-legacy`，該 profile 把新加入的模組全部設 `modules.[new]: false`
- 預期：所有既有模組測試仍全綠
- 若此 gate 失敗 → 表示新模組對舊模組造成編譯或執行期影響 → PR 不得合併

```yaml

    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '21'
```

### 8.7 回歸測試策略

**核心原則**：每次引入新模組，都要證明「舊模組沒壞」。

**三層回歸範圍**：

| 層級 | 觸發時機 | 範圍 | 時間預算 |
|------|---------|------|---------|
| **L1 快速回歸** | 每次 PR 提交 | 被修改模組的單元測試 + 直接依賴模組的單元測試 | < 5 分鐘 |
| **L2 整合回歸** | merge 至 `develop` | 所有模組單元測試 + 跨模組整合測試 + 所有 Testcontainers 場景 | < 20 分鐘 |
| **L3 完整回歸** | 每 Phase 結束、每日排程 | L2 + E2E 業態快樂路徑 + 壓測基準 + sync-validation | < 60 分鐘 |

**識別受影響模組的方法（自動化）**：
1. 解析 PR 的 `git diff --name-only` 取得變更檔案
2. 映射檔案 → 模組（例如 `backend/module-pos-core/` → `module-pos-core`）
3. 查閱 `pom.xml` 找出反向依賴（哪些模組 depends on 變更模組）
4. 查閱變更模組發布的 Events，`grep -r "@EventListener.*XxxEvent"` 找消費者
5. 查閱變更模組的選配依賴 `@Autowired(required = false)` 使用者
6. 集合這些模組的測試為 L1 範圍

**必保留的回歸測試清單（Critical Path）**：

每個模組至少一個測試方法必須通過，否則整個 CI 失敗：

| 模組 | 回歸關鍵測試 |
|------|-------------|
| `module-auth` | `AuthServiceTest#loginSuccess`、`PosAuthServiceTest#pinLoginSuccess`、`PermissionServiceTest#checkPermission` |
| `module-organization` | `StoreServiceTest#createStore`、`TerminalServiceTest#registerTerminal`、`TerminalOfflineEventIT` |
| `module-workflow` | `WorkflowEngineTest#startAndApprove`、`WorkflowEngineTest#rejectAndNotify` |
| `module-notification` | `NotificationServiceTest#sendWebSocket` |
| `module-pos-core` | `OrderServiceIT#completeOrderFlow`、`PricingEngineTest#calcWithDiscountAndTax`、`RefundServiceIT#refundFlow` |
| `module-pos-product` | `BarcodeQueryServiceTest#findByBarcode`、`ProductServiceIT#createItemWithVariants` |
| `module-pos-payment` | `CashGatewayTest#pay`、`ReconciliationServiceIT#dailyReconcile` |
| `module-pos-tax` | `InvoiceNumberAllocatorTest#allocate`、`MigFormatterTest#formatInvoice` |
| `module-pos-inventory` | `StockDeductionServiceIT#concurrentDeduction`、`TransferServiceIT#approvalFlow` |
| `module-pos-staff` | `XReportCalculatorTest#calculate`、`ZReportCalculatorTest#calculateWithHash` |

**回歸失敗處理 SOP**：
1. CI 標紅 → PR 阻擋 merge
2. 作者先自查：是否真的改壞既有行為？是 → 改回去或修正
3. 若判定是老測試過期（需求改變導致）→ 開獨立 PR 更新測試 → 取得被影響模組 owner approve
4. 禁止直接刪除 / @Disabled 既有測試而不走流程

### 8.8 異常隔離與模組崩潰防護

**為何需要**：所有模組在同一 JVM 下跑，任一模組 Memory Leak / Deadlock / OOM 會拖垮全系統。核心模組（auth、organization、pos-core）必須在周邊模組出錯時仍能繼續運作。

**隔離層級**（由淺入深）：

**1. Bean 級隔離 — 編譯期**
- `@ConditionalOnModule("xxx")` 確保模組關閉時 Bean 不載入
- 核心模組（P0）的 `matchIfMissing = true`，周邊模組（P1-P3）`matchIfMissing = false`
- 結果：單一模組 class loading 失敗不影響其他模組啟動

**2. 執行緒池隔離 — 運行期**
- 為高流量模組配置獨立 `ThreadPoolTaskExecutor`：

```java
@Configuration
public class PosCoreAsyncConfig {
    @Bean("posCoreExecutor")
    public ThreadPoolTaskExecutor posCoreExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(20);
        executor.setMaxPoolSize(50);
        executor.setQueueCapacity(500);
        executor.setThreadNamePrefix("pos-core-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        return executor;
    }
}
```

- `@Async("posCoreExecutor")` 明確指定執行池
- 受保護的模組：`pos-core`、`pos-payment`、`pos-printing`、`pos-sync`、`notification`
- 結果：A 模組的執行池滿不會堵到 B 模組

**3. 外部呼叫斷路 — Resilience4j**
- 所有外部系統呼叫必須包 CircuitBreaker + Timeout + Bulkhead + Retry：

```java
@CircuitBreaker(name = "taxGateway", fallbackMethod = "issueInvoiceFallback")
@TimeLimiter(name = "taxGateway")
@Bulkhead(name = "taxGateway", type = Bulkhead.Type.SEMAPHORE)
public CompletableFuture<Invoice> issueInvoice(Order order) { ... }

public CompletableFuture<Invoice> issueInvoiceFallback(Order order, Throwable t) {
    // 排隊延後重試，不讓訂單流程卡住
    invoicePendingQueue.enqueue(order);
    return CompletableFuture.completedFuture(Invoice.pending());
}
```

- 受保護對象：`module-pos-tax`（財政部）、`module-pos-payment`（LINE Pay/街口）、`module-pos-delivery`（Uber Eats）、`module-pos-printing`（實體印表機）

**4. 資料庫連接池隔離**
- 主連接池（HikariCP）給交易類模組：`maximumPoolSize: 30`
- 考慮為 `module-pos-report` 分配次要連接池（長查詢不搶主池連線）
- Phase 2 Sprint 2-4 評估是否需要

**5. 事件處理異步化**
- 所有 `@EventListener` 用 `@Async("eventExecutor")` 執行
- 訂閱者崩潰 → 例外被吞在執行緒池，不回饋給發布者
- 重要事件額外寫入 `event_outbox` 表（Transactional Outbox Pattern），由排程補發

**6. 記憶體與健康監控**
- Spring Boot Actuator: `/actuator/health`、`/actuator/metrics`、`/actuator/prometheus`
- 每個模組實作 `HealthIndicator`：

```java
@Component("posCoreHealth")
public class PosCoreHealthIndicator implements HealthIndicator {
    public Health health() {
        // 檢查 pos-core 關鍵 Bean、DB 連線、Redis 連線
        return Health.up().withDetail("module", "pos-core").build();
    }
}
```

- Grafana 儀表板監控：JVM Heap、GC 次數、各模組 Thread pool 使用率、DB 連接池使用率
- OOM 時自動 dump heap：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/pos/heap.hprof`

**7. 模組崩潰的降級策略（Graceful Degradation）**

| 崩潰模組 | 對核心影響 | 降級行為 |
|---------|----------|---------|
| `module-pos-printing` | 無法列印收據 | 自動切 Mock printer + WebSocket 通知管理員；訂單仍可完成 |
| `module-pos-tax` | 無法開電子發票 | 訂單完成 + 發票排隊等重試；超過 48 小時補開 |
| `module-pos-crm` | 無法累點 | 結帳流程跳過累點邏輯，事後補點數（由事件 replay）|
| `module-pos-promotion` | 無法套用促銷 | 結帳以原價計算，前端顯示「促銷暫停」 |
| `module-notification` | 無法推播 | 通知寫入 DB 佇列，WebSocket 恢復時補發 |
| `module-pos-sync` | 離線同步失敗 | 終端改用本地 SQLite 繼續營業，重連後衝突解決 |
| `module-pos-hardware` | 錢箱/讀卡機失效 | UI 顯示告警；允許手動輸入代替 |

**8. 啟動順序保護**
- `@DependsOn` 明確宣告啟動順序（auth、organization 最先；pos-core 其次；周邊模組最後）
- `ApplicationReadyEvent` 後才開放流量（健康檢查未通過前 LB 不導流）

## 十、驗證方式（每 Phase 結束跑一次）

1. **後端**（工作目錄 `POS/backend/`）：
   - `cd /Users/wei/Desktop/code/POS/backend && mvn clean verify`

   - 驗證 `curl http://localhost:8080/actuator/health` 回 `{"status":"UP"}`
   - Flyway migration 紀錄比對（`flyway_schema_history` 表）

2. **前端**（工作目錄 `POS/frontend-web/`）：
   - `cd /Users/wei/Desktop/code/POS/frontend-web && npm run build && npm run test`
   - `npm run dev` → 手動走一次「登入 → 商品 → 訂單 → 退款」快樂路徑
   - 檢查 `NotificationBell` 可接收推播

   - Phase 1 → 零售門市 `--spring.profiles.active=retail`
   - Phase 2 → 速食餐飲 `--spring.profiles.active=fastfood`
   - Phase 3 → 咖啡廳 `--spring.profiles.active=cafe`
   - Phase 4 → 正式餐廳 `--spring.profiles.active=restaurant`

4. **Flutter POS**（Phase 3 起，工作目錄 `POS/frontend-app/`）：
   - `cd /Users/wei/Desktop/code/POS/frontend-app && flutter run -d ipad`
   - 手動驗證：PIN 登入 → 建立訂單 → 離線模式 → 恢復連線同步

5. **模塊化組件同步驗證**（每 Sprint 結束）：
   - 確認所有可複用改動已複製至 `模塊化組件/module/` 對應位置
   - `cd /Users/wei/Desktop/code/POS/模塊化組件/module/backend && mvn clean compile` 確認元件庫本身可獨立編譯
   - 在 [模塊化組件/devlog/](模塊化組件/devlog/) 新增一筆同步紀錄
