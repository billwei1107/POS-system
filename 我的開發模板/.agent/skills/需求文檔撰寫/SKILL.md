# 需求文檔撰寫 Skill

## 概述

本 Skill 定義了從「用戶原始需求輸入」到「產出標準化需求文檔」的完整流程。  
當用戶提供一個新專案的需求描述（口頭、文字、截圖、參考網站等任何形式）時，AI 助手必須嚴格按照以下步驟執行。

---

## 第一步：需求收集與釐清 (Requirement Gathering)

### 1.1 閱讀並理解用戶輸入

- 仔細閱讀用戶提供的所有需求資料（文字、圖片、連結等）。
- **不要急於動手**，先完整理解用戶的商業意圖與目標。

### 1.2 建立需求理解摘要

閱讀完所有輸入後，必須先向用戶輸出一份「需求理解摘要」，格式如下：

```markdown
# 需求理解摘要

## 專案背景
[用一段話描述你理解的專案背景和商業目的]

## 核心目標
1. [目標 1]
2. [目標 2]
3. ...

## 目標用戶
- 用戶角色 A：[描述]
- 用戶角色 B：[描述]

## 功能範圍 (初步判斷)
| 功能模塊 | 簡述 | 優先級 |
|---------|------|--------|
| [模塊名] | [一句話描述] | P0/P1/P2 |

## 待確認問題
1. [任何不確定的需求點]
2. [需要用戶補充的細節]
```

### 1.3 等待用戶確認

- **必須**等待用戶對摘要的確認或修正。
- 若用戶有修正，更新摘要後再次確認。
- **禁止**在用戶未確認前開始撰寫正式需求文檔。

---

## 第二步：功能拆解 (Feature Decomposition)

### 2.1 模塊化拆分

根據確認後的需求，將系統拆分為獨立的功能模塊。拆分原則：

1. **按業務領域拆分**：例如「用戶管理」、「訂單管理」、「報表系統」
2. **按用戶角色拆分**：例如「前台（客戶端）」、「後台（管理端）」
3. **每個模塊獨立可描述**：一個模塊 = 一組相關功能的集合

### 2.2 功能細項列舉

每個模塊下，列出所有功能細項。每個細項必須包含：

| 欄位 | 說明 | 範例 |
|------|------|------|
| 功能名稱 | 簡短動詞 + 名詞 | 新增訂單 |
| 描述 | 一句話說明做什麼 | 用戶可填寫表單建立新的訂單 |
| 輸入 | 該功能需要哪些輸入資料 | 客戶名稱、聯絡電話、地址、品項清單 |
| 輸出 | 該功能產出什麼結果 | 訂單編號、訂單確認頁面 |
| 業務規則 | 特殊邏輯或約束 | 訂單金額 > 10000 需主管審核 |
| 優先級 | P0 (必備) / P1 (重要) / P2 (次要) | P0 |

### 2.3 非功能需求收集

除了功能需求，必須明確以下非功能需求：

```markdown
## 非功能需求

### 效能需求
- 頁面載入時間：[< 3 秒 / < 5 秒]
- 並發用戶數：[預估值]
- 資料量級：[預估筆數]

### 安全需求
- 認證方式：[JWT / Session / OAuth]
- 密碼策略：[BCrypt / Argon2]
- 敏感資料處理：[加密方式]
- API 授權：[RBAC / ABAC]

### 相容性需求
- 瀏覽器支援：[Chrome/Safari/Firefox 最新版]
- 行動裝置：[iOS 版本 / Android 版本]
- 螢幕尺寸：[響應式 / 固定寬度]

### 可用性需求
- 多語系：[是否需要 i18n]
- 無障礙：[WCAG 等級]
- 離線功能：[是否需要]
```

### 3.2 撰寫原則

1. **具體優於抽象**：「用戶可上傳 JPG/PNG 圖片，單檔上限 5MB」比「用戶可上傳圖片」好
2. **量化優於定性**：「載入時間 < 3 秒」比「載入要快」好
3. **場景優於描述**：用「前置條件 → 操作步驟 → 預期結果」的結構描述功能
4. **不遺漏錯誤處理**：每個功能都要定義異常情境的處理方式
5. **優先級明確**：P0 = 沒有就不能用、P1 = 重要但可後做、P2 = 錦上添花

## 第四步：用戶確認與迭代

### 4.1 提交審閱

- 完成需求文檔後，**必須**通知用戶審閱。
- 明確告知用戶需要確認的重點：功能範圍、優先級、技術選型。

### 4.2 修訂流程

- 用戶的修改意見必須逐一回應與處理。
- 每次修訂後更新「變更紀錄」區塊。
- 最終版本需用戶明確確認後，將狀態改為「已確認」。

### 4.3 產出後續文檔的觸發

需求文檔確認後，應提示用戶：
- 接下來可使用 **開發流程設計 Skill** 產出流程圖與設計圖
- 可使用 **客戶測試流程 Skill** 產出客戶測試文檔

---

## 第五步：同步更新關聯文件

1. 更新 `devlog/devlog.md` 中的「開發規劃」區塊
2. 在當日 devlog (`devlog/YYYY-MM-DD-devlog.md`) 記錄需求文檔完成的時間
3. 若有待確認問題尚未解決，在 `devlog/troubleshooting.md` 中記錄

---

## 注意事項

> [!CAUTION]
> - **禁止**跳過「需求理解摘要」直接撰寫正式文檔
> - **禁止**在用戶未確認摘要前開始寫正式需求
> - **禁止**遺漏非功能需求（安全、效能、相容性）
> - **禁止**功能描述只寫「名稱」不寫「操作步驟」和「業務規則」
> - 所有需求文檔**必須**存放於 `需求/` 目錄
