# POS 開發進度對照

> **更新時間**: 2026-05-11 01:23 CST
> **用途**: 作為 `開發流程規劃.md` 的執行狀態表。之後每次開發前先看本文件，確認目前 Sprint、完成度、MVP 與下一步。

## 目前策略

目前專案已不再是空白 bootstrap，已有多個 POS 模組與前端頁面。實際開發策略調整為：

1. 先補齊「咖啡廳 POS 可操作主流程」：登入 → 商品 → 購物車 → 折扣/會員 → 掛單 → 結帳 → 現金找零 → 訂單紀錄。
2. 已做成 MVP 的流程，後續再依 `開發流程規劃.md` 回補正式後端模組、資料表、測試與母體同步。
3. 每次繼續開發前，先確認本文件的「下一步建議」，避免偏離 Phase/Sprint 主線。

## MVP 需正式化

| MVP | 目前做法 | 正式化目標 |
|-----|----------|------------|
| 會員 | `DEMO_POS_MEMBERS` 前端假資料 | 建立 `module-pos-crm`，提供會員查詢、綁定、點數、等級折扣 API |
| 掛單 | 後端 `pos_held_orders` API，localStorage 作備援 | 補多終端併發、過期清理、取回權限與操作審計 |
| 折扣 | 手動折扣與會員折扣互斥 | 接 `module-pos-promotion`，建立折扣來源、堆疊規則與審計紀錄 |
| 現金付款 | 前端 tendered → core complete API | 接 `module-pos-payment` 的 payment transaction、cash drawer、reconciliation |
| 收銀台 Web UI | React web 先跑主流程 | Phase 3 建 Flutter POS terminal；Web 可保留為測試/管理模式 |

## 缺口與風險

| 類型 | 缺口 | 影響 |
|------|------|------|
| 測試 | 前端尚未建立 Vitest/RTL/MSW 基線 | shared 與 POS UI 邏輯目前主要靠 build + Playwright |
| 後端整合 | 尚未全量跑 `mvn verify` / Testcontainers | 跨模組事件、Flyway 全量相容性需補強 |
| 模組同步 | POS 內可復用修正尚未逐項同步回母體 | 模塊化組件正式導入其他專案前需整理 |
| 掛單 | 已可跨刷新由後端取回，但尚未補權限與過期策略 | 多終端併發取回、不同操作員權限、逾期掛單清理仍需設計 |
| 會員 | 目前不查後端會員資料 | 無真實會員建立、點數、儲值、消費歷史 |
| 支付 | 現金找零未寫入 `pos_pay_transactions` happy path 驗證 | 對帳、錢櫃、Z Report 會缺資料來源 |
| 稅務 | 訂單完成未完整驗證發票流程 | Phase 1 零售交付準則尚未滿足 |

## 下一步建議

1. **先接 Sprint 1-3 payment transaction**
   - 結帳完成時建立 `pos_pay_transactions`。
   - 現金付款寫入 tendered/change。
   - 補對帳頁可以看到該筆付款。

2. **再接 Sprint 1-4 tax happy path**
   - 訂單完成後自動建立 mock invoice。
   - 前端可在訂單或發票頁查到。

3. **補掛單正式營運細節**
   - 多終端同時取回同一掛單的鎖定策略。
   - 掛單過期清理與操作員權限。
   - 後台查詢與審計紀錄。

4. **最後補 Phase 0 測試基線**
   - Vitest/RTL/MSW。
   - `cartStore`、`moneyFormat`、`CheckoutPage` 關鍵邏輯測試。

## 後續開發執行規則

- 每次「繼續開發」前，先讀本文件與 `開發流程規劃.md` 對照。
- 每次完成前端或使用者流程，必須重建 frontend 並用瀏覽器實測。
- 若某功能只是 MVP，必須在本文件標記，不視為正式 Sprint Done。
- 真正 Sprint Done 需同時滿足：後端 API、前端頁面、測試、Docker 驗證、devlog、必要時同步母體。
