## POS Web 端

### 收銀台

- 收銀台目前以觸控操作為主要設計方向，商品可直接點擊加入右側購物車。
- 手機版已改成購物車需要打開的形式，但上方排版仍可再調整。
- 折扣與會員入口已出現在收銀台，但會員功能目前仍偏手動。
- 會員後續應支援：
  - 條碼機掃描會員。
  - 會員查找頁或彈窗。
  - 點數累積與消費紀錄查詢。
- 付款頁右側已預留行動支付或其他支付方式，但尚未正式接入。
- 結帳後訂單列表可看到購買項目與細項資料。

### 訂單列表 UI

- 訂單列表目前有欄位文字換行問題，例如訂單編號、品項、付款狀態、建立時間或操作欄位擠壓。
- 建議表格欄位維持單行顯示，不要自動斷行。
- 資料過長時，列表應支援水平捲動。
- 重要欄位應放在左側，必要時可固定不跟著水平捲動。
- 常用操作不一定要塞在獨立操作欄：
  - 點擊整列可以直接開啟查看或編輯彈窗。
  - 操作按鈕可以減少，避免表格右側過擠。

### 主題與視覺

- 目前 POS 主要是深色介面。
- 後續應補亮色模式，並支援深色 / 淺色切換。
- 右上角操作員區塊的文字與 UI 擁擠，需要細節打磨。
- 商品管理頁面目前功能可用，但視覺上仍需優化。

## 商品、庫存與發票

### 商品管理

- 新增商品不應只靠手動輸入，應思考自動填入或匯入能力。
- 商品應能連結材料與庫存。
- 餐飲或零售商品通常需要定義用料：
  - 一個商品會用到哪些材料。
  - 每個材料使用多少數量。
  - 商品售出後如何扣庫存。
- SKU 不應隨意輸入，應有定義規則。
- 若 POS 要做成泛用系統，SKU 規則可以設計成可配置，而不是寫死咖啡店或單一產業。

### 庫存

- 目前已有庫存總覽、盤點、進貨驗收與數量調整等方向。
- 盤點單需要顯示進度、品項、差異與盤點數量。
- 盤點完成後，庫存應以盤點結果同步更新。
- 進貨驗收後，後續應與材料 / 商品庫存連動。

### 發票

- 發票資料應從訂單產生後同步進發票模組。
- 發票號碼目前尚未定義，後續需補規則與資料流。
- 發票功能最後可能更適合整合進訂單流程，而不是完全獨立。

## 前台與後台分工

- 前台 POS 應聚焦收銀、會員、折扣、付款、訂單查詢。
- 後台應處理：
  - 商品管理。
  - 庫存管理。
  - 進貨 / 盤點。
  - 班次與對帳。
  - 權限管理。
- 目前後台功能與前台部分頁面相近，後續應拉開定位，避免兩邊重複。

## App 端

- 目前 App 已有頁面雛形，但還沒有真正進去完整實測。
- 開發策略先以 Flutter Android 為主。
- 尚未有 Apple Developer 帳號，因此 iOS 實機與正式發佈先不是當前重點。
- POS 系統最重要的場景是平板，不只是手機。
- 後續應找 Android 平板或至少用平板模擬器做實際操作測試。

- 班次功能應與員工、每日交易金額、錢櫃或收款金額對帳連動。
- 重點是能檢查當日交易與實際收款是否吻合。

## 模組化與組件庫

### 後端模組

- 目前已有後端模組化倉庫，並用 agent / workflow 從遠端倉庫抽取需要的模組。
- 後續仍需補更多測試，確認模組在不同專案導入時穩定。

### 前端組件庫

- 建議建立前端組件庫，讓未來不同系統可重用一致的 UI 元件。
- 組件庫價值不小，尤其能統一設計風格，減少每個專案重寫基本元件。
- 優先可抽：
  - Button。
  - Input。
  - Calendar / 行事曆。
  - Date picker / Time picker。
  - Icon button。
  - Modal / Drawer。
- 每個組件應支援：
  - 尺寸大小。
  - 文字內容。
  - 上下左右 padding。
  - 顏色與 icon。
  - 預設狀態、hover、disabled、loading 等狀態。
- 組件庫可以打包成 npm package。
- 可用 GitHub Actions 在 push 後自動 build / test / publish 到 npm registry。
- 使用端專案可用 npm 或 pnpm 安裝。
